Lesson 34: A corpus that becomes a wiki, and survives an edit

one corpus → surfaces → wiki projection → adopted ontology → a cache that survives an edit

1. Why This Feature Exists

A documentation folder is the cheapest knowledge base a team already has. This example turns five markdown pages, one memory fact and one todo into a single graph, renders the wiki a human reads, and then edits the world under it — twice — to show what is derived, what is adopted, and what survives:

2. What the Example Demonstrates

A — SURFACES
wikiSurface() imports the folder as section nodes plus references edges (a dangling [[link]] is data, not an error), and the read-only memory / todos adapters merge in through surfaceFragment() + mergeFragment(). Nothing is written back.
B — RENDER
renderWiki() writes one page per node; the index carries graph-sha256, which is how staleness is proved.
C — ROUTE
a model, given only the rendered map, routes a 429 question to one page and answers from it.
D — STALE
any edit after a render is a wiki-stale finding; only a re-render clears it.
E — ONTOLOGY
profileSources() measures the corpus, proposeOntology() proposes kinds and relations with the evidence for each, adoption is versioned and compare-and-swapped, and the graph is rebuilt inside it.
F — CACHE
syncCorpus() writes manifest.json; an unchanged corpus costs nothing, and an edited file rebuilds only the mechanical layer while the model's nodes are re-anchored by content key.
G — ORPHAN
remove the paragraph a node was derived from and the node is dropped — provenance that no longer resolves is not kept. What this shows: - one store, two projections: the wiki is a view, not a second database; - read-only surfaces: memory and todos are indexed without being written; - an ontology with evidence, adopted as a versioned, swappable act; - a delta rebuild that treats the agent's work as data.
