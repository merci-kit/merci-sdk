Lesson 37: Your SDK is the MCP server

your SDK as an MCP server over Streamable HTTP, capabilities, artifacts, loadable components

1. Why This Feature Exists

This process does not consume someone else's MCP server; it IS one. A node:http server serves the Streamable HTTP transport from createMcpHttpHandler, and a real model on the other side of an McpClient calls the tools this same process advertises — the same model wearing two hats, server-side and client-side.

2. What the Example Demonstrates

A — serve
createMcpHttpHandler mounts word_stats (with an outputSchema) on a loopback node:http server.
B — connect
an McpClient attaches over Streamable HTTP and loadMcpTools maps the advertised tool into an SDK tool; a direct call returns the server's own numbers.
C — the model calls
a live session uses that remote tool and answers with the forced marker plus the real word count.
D — the extension surface
a LoadableComponent (loaded, saved and injected as a per-step block), an ExternalToolCapability doing real file work, and an AcpCapability over a duck-typed client — all registered on one session with withCapability.
E — bounded output
capToolOutput on text, capToolOutputValue on JSON, with the truncation suffix the model actually sees.
F — artifacts
createSaveArtifactTool writes versioned files and keeps a manifest, so a large result becomes a path.
G — host context
buildEnvironmentBlock + discoverInstructions render the workspace block and the AGENTS.md a host injects.
